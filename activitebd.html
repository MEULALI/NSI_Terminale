Bases de données / Chapitre 1

Modèle relationnel

Introduction

Le développement de traitements informatiques nécessite la manipulation de données de plus en plus nombreuses. Leur organisation et leur stockage constituent un enjeu essentiel de performance.

Question centrale : Comment gérer (mémoriser et traiter) un ensemble volumineux de données ?

Modèle relationnel

Les bases de données relationnelles sont basées sur ce qu’on appelle le modèle relationnel. Il s’agit d’un modèle logique (basé sur des concepts mathématiques) défini en 1970 par l’informaticien britannique Edgar F. Codd (1923-2003), lors de ses travaux chez IBM. Il a reçu le prix Turing en 1981.

Le modèle relationnel est une manière de modéliser les relations existantes entre plusieurs informations et de les ordonner entre elles. Il est basé sur des relations.

Relation, attribut, domaine, schéma

Prenons l’exemple d’un disquaire permettant d’emprunter des albums de musique. L’ensemble de ses albums peut être représenté par l’ensemble :

Album = {
    ("I Still Do", "Eric Clapton", 2016, Vrai),
    ("Axis: Bold as Love", "Jimi Hendrix", 1967, Faux),
    ("Continumm", "John Mayer", 2006, Faux),
    ("Riding With The King", "Eric Clapton et B.B. King", 2000, Faux),
    ("Don't explain", "Joe Bonamassa et Beth Hart", 2011, Vrai),
    ...
}

Un tel ensemble s’appelle une relation (la relation Album en l’occurrence).

Attention : cette relation Album n’est pour le moment pas satisfaisante ! Nous verrons plus loin pourquoi et comment y remédier.

Les différents éléments d’une relation s’appellent des enregistrements (ou tuple, n-uplet, t-uplet, ou vecteur). Les enregistrements d’une relation possèdent les mêmes composantes, que l’on appelle les attributs de la relation.

Une relation se conforme toujours à un schéma qui est une description indiquant pour chaque attribut de la relation son nom et son domaine (= le « type » de l’attribut : un entier, une chaîne de caractères, une date, etc.).

Ainsi, pour le moment, la relation Album possède 4 attributs :

  • titre : le titre de l’album, une chaîne de caractères ;
  • artiste : le ou les artistes de l’album, une chaîne de caractères ;
  • annee : l’année de parution de l’album, un entier naturel ;
  • dispo : disponibilité de l’album, un booléen.

Base de données relationnelle

Une base de données relationnelle est un ensemble de relations. Par exemple, la base de données de notre disquaire ne contiendra pas uniquement la relation Album. Elle peut par exemple contenir deux autres relations : Client et Emprunt qui correspondent respectivement à l’ensemble des clients du disquaire et à l’ensemble des emprunts en cours.

Le schéma, ou la structure, d’une base de données relationnelle est l’ensemble des schémas des relations de la base. Ainsi, pour le moment, la structure de la base de données du disquaire est :

  • Album(titre TEXT, artiste TEXT, annee INT, dispo BOOL)
  • Client(...)
  • Emprunt(...)

Concevoir la structure d’une base de données relationnelle

La conception de la structure d’une base de données n’est pas toujours aisée mais c’est un travail absolument nécessaire pour obtenir une base ne souffrant d’aucune anomalie et offrant des performances optimales.

On trouve en général ces trois étapes :

  1. Déterminer les entités (objets, actions, personnes, …) que l’on souhaite manipuler.
  2. Modéliser chaque ensemble d’entités comme une relation en donnant son schéma : attributs et domaine de chaque attribut.
  3. Définir les contraintes d’intégrité (domaine, relation, référence) de la base de données, c’est-à-dire toutes les propriétés logiques vérifiées par les données à chaque instant.

Domaine d’un attribut et contrainte de domaine

Le domaine d’un attribut est le « type » de l’attribut. Concrètement, un SGBD doit s’assurer à chaque instant de la validité des valeurs d’un attribut : ce sont les contraintes de domaine. Si un attribut a pour domaine INT et que l’on essaie de saisir une valeur de type FLOAT, cela provoquera une erreur.

Attention aux choix de domaines : Si le domaine d’un attribut correspondant à un code postal est INT, alors l’enregistrement du code postal 05000 deviendra 5000 (car 05000=500005000 = 500005000=5000 pour les entiers). Il est donc nécessaire de donner le domaine TEXT à un code postal.

Clé primaire

Définition : Une clé primaire est un attribut (ou une réunion d’attributs) qui permet d’identifier de manière unique un enregistrement d’une relation.

La relation Album

Dans notre relation Album initiale, aucun attribut ne peut jouer le rôle de clé primaire (plusieurs albums peuvent avoir le même titre, le même artiste, ou la même année de sortie).

Pour y remédier, on crée « artificiellement » un attribut id_album (de type INT) qui jouera le rôle de clé primaire. Pour symboliser la clé primaire dans le schéma d’une relation, on la souligne (ou on la met en gras) :

Contrainte de relation

La contrainte de relation impose que chaque enregistrement d’une relation soit unique. C’est la présence d’une clé primaire dans chaque relation qui permet de réaliser cette contrainte.

Définition : Une clé étrangère d’une relation est un attribut qui est clé primaire d’une autre relation de la base de données.

Dans Emprunt, id_client et id_album sont des clés étrangères (référençant les tables Client et Album).

Redondance des données

Une relation ne doit pas contenir d’informations déjà disponibles dans d’autres relations. Dans la première version d’ Emprunt, conserver nom, prenom, email, titre, artiste, etc. crée de la redondance inutile.

Les clés étrangères suffisent à faire le lien vers d’autres tables. On note les clés étrangères avec le symbole #. Une version satisfaisante de la relation Emprunt est :

Pourquoi éviter la redondance des données ?

  1. Coût en mémoire et performances : Répéter des chaînes de caractères consomme du stockage et ralentit les requêtes.
  2. Cohérence des données : Si un client change de nom ou d’adresse email, la modification s’effectue à un seul endroit (dans la table Client) sans risquer d’incohérences.

Contrainte de référence

Les clés étrangères permettent d’assurer les contraintes de référence :

  • Une valeur de clé étrangère doit obligatoirement exister comme clé primaire dans la table référencée.
  • Un enregistrement ne peut être effacé de sa table d’origine si sa clé primaire est référencée ailleurs dans une clé étrangère.
  • Une clé primaire ne peut être modifiée si elle est utilisée dans d’autres tables.

Bilan

  • Utilisation des BDD : Les fichiers CSV ou texte simples ne suffisent pas pour des volumes importants. Un SGBD permet de gérer, stocker et manipuler des bases de données de façon performante.
  • Modèle relationnel : Basé sur des relations (tables). Une relation comporte des enregistrements (lignes) et des attributs (colonnes), chacun associé à un domaine (type).
  • Clé primaire : Permet d’identifier chaque enregistrement de manière unique et garantit la contrainte de relation.
  • Clé étrangère : Permet d’associer deux relations et garantit la contrainte de référence, tout en évitant la redondance des données.
  • Conception : Étape essentielle pour éliminer les anomalies d’insertion, de suppression et de mise à jour.
